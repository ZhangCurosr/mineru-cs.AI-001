# 论文速读：VAKRA: Evaluating Multi-Hop Reasoning Across APIs and Retrieval Under Tool-Use Policies

## 一句话总结
论文提出了 VAKRA 基准，用于在可执行环境中评估智能体跨 API 和文档集合的多跳推理能力，涵盖三种递进难度的任务设置（多样化 API 交互风格、多跳结构化 API 推理、带自然语言工具使用策略约束的多源推理），并通过重放预测的工具调用序列进行轨迹级验证。实验表明，即使最先进模型在单跳端点式任务上表现尚可（GPT-5.5 达 70.4%），但在组合式 API 和策略约束任务上性能显著下降，跨源实体消歧、模式对齐等语言中介推理步骤是主要瓶颈。

## 研究问题与动机
- **企业智能体的复合推理需求**：实际部署的企业智能体需同时处理结构化 API 调用与非结构化文档检索，并在自然语言策略约束下进行多跳推理（如客服场景中跨 CRM、物流 API、文档政策的多步交互），但现有基准往往孤立评估工具调用、检索或策略遵循能力。
- **现有基准的局限性**：多数工具调用基准依赖合成环境或外部不稳定 API（如 ToolBench、RestBench），或仅测试嵌套 API 序列（如 NESTFUL）而缺乏跨源 grounding；多跳推理基准（如 ToolHop）未结合真实数据库与文档集合；策略遵循基准（如 τ-bench）局限于窄域对话，且评估指标无法区分中间推理步骤的错误类型。
- **缺乏可复现的确定性评估**：许多基准的 API 行为会随时间变化，无法保证评估时的确定性和可重放性，导致模型比较困难。
- **评估粒度不足**：传统基准多以最终答案正确性评分，无法定位智能体在多跳推理链中具体失败环节（如实体消歧、参数提取、策略解释）。

## 核心贡献（创新点）
- **首个集成可执行 API 与文档检索的真实基准**：构建超过 8,000 个可执行 Python API（源自 62 个 BIRD-SQL 领域）、62 个语义聚类的领域专属文档集合（基于 Wikidata5M 和 ClapNQ），并提供轨迹级验证框架——重放预测工具调用序列并与真实 API 交互，允许路径等价性。
- **三种递进难度的多跳推理任务设置**：设计多样性 API 交互风格（SLOT 通用组合式、SEL 扩展函数式、Dashboard 端点式）、多跳结构化 API 推理（2–5 跳，依赖前序结果参数化后续调用）、带自然语言工具使用策略的多源推理（要求智能体在 API 与文档检索间切换，并遵守约束如“不得使用文档回答电影相关问题”）。
- **隔离模型能力与架构的工程化评估管道**：使用固定 ReAct 智能体骨架（LangGraph ReAct + MCP 协议），将所有模型（开源与闭源）包裹在同一抽象接口中，确保分数差异源于模型本身而非编排逻辑；提供 Docker 化自托管环境，工具列表经过 SHA-256 校验防止漂移。
- **详细的错误分析与发现**：通过逐阶段筛除分析（工具名称→参数名→参数值→接地答案）揭示不同 API 风格下的错误分布差异；指出失败集中于语言中介推理（实体消歧、跨源对齐、模式映射）而非工具调用机械操作，并量化幻觉与提取错误的比例。

## 方法详解
- **数据集构建**：
  - **API 环境**：将 BIRD-SQL 数据库转换为可执行 Python 函数（遵循 Elder et al. (2026) 的生成管线），并为每个工具生成增强的自然语言描述；按三种风格抽象：SLOT（9 个通用工具，参数槽位填充）、SEL（26 个预实例化工具）、Dashboard（每样本 116 个专用端点）。
  - **多跳查询生成**：四阶段管线——① 从 BIRD-SQL 查询抽取命名实体并映射至 Wikidata5M 标识符构建领域知识图谱；② 基于实体兼容性构建查询连接图，深度优先遍历生成 1–3 跳 API 链（采样权重 0.10/0.60/0.30），用 LLM 合并子查询生成多跳问题；③ 引入 Wikipedia 段落作为检索增强链接，生成 API+RAG 组合问题；④ 生成纯检索多轮对话并进行跨源可答性过滤（确保 RAG 问题不能仅靠 API 回答，反之亦然）。
  - **检索索引**：使用 LLM 过滤掉能回答任意 API 查询的文档，剩余文档按领域用 ChromaDB 索引（每域 2 万份）。
- **评估框架**：
  - **瀑布式三阶段验证**：① 工具序列验证：重放每个预测工具调用至真实环境，通过程序性包含检查（ground truth 信息是否全部恢复）与 LLM judge（基于 CRAG 框架）判断轨迹是否正确；② 最终响应评估：仅对通过阶段一的轨迹，用 LLM judge 检查答案的事实一致性与接地性；③ 策略遵循验证：确定性检查是否使用了禁止的数据源。
  - **执行环境**：单一 Docker 镜像（`benchmark_environ`）内含四种能力容器（API 风格×3、多跳多源×1），通过 MCP over stdio 通信；数据库与原始索引不暴露给智能体，嵌入模型（IBM granite-embedding-english-r2）在镜像内固化。
  - **智能体实现**：所有模型包裹为 LangGraph ReAct 智能体（`AgentInterface` 统一接口），工具定义经 MCPToolWrapper 转为 LangChain StructuredTools；可选 ToolShortlister 基于句子Transformer 为查询过滤 top‑k 工具。
- **质量保障**：对多跳与多跳多源样本进行人工标注（60 题/设置 × 62 域 × 5 维度×1–4 分制），合格率 87%（多跳）与 96%（多源）； annotator 一致率 77%–90%。

## 实验与结果
- **数据集统计**：调优集共 3,464 样本（SEL 710、SLOT 614、Dashboard 1,860、多跳 346、多源 898）；测试集共 2,308 样本（SEL 549、SLOT 33、Dashboard 1,00、多跳 38、多源 41），覆盖 62 域、7,087 个工具。
- **模型评测**：评估 11 个前沿/开源模型（GPT‑5.5、Claude‑Opus‑4.7、Gemini‑3‑Flash‑Preview、Claude‑Sonnet‑4.5、GLM‑5.1、Qwen‑3.5‑397B、GPT‑OSS‑120B、LLaMA‑405B、Qwen‑2.5‑72B‑Instruct、Granite‑4h‑small、LLaMA‑3.3‑70B‑Instruct）。
- **主要结果**（Table 3）：
  - **API 风格**：Dashboard 任务最容易（GPT‑5.5 70.4%，其他模型 46–60%）；组合式 BI API 更难（SEL 51.0%、SLOT 50.0% for GPT‑5.5）；中等规模模型有时优于大型开源模型（如 Qwen2.5‑72B 在 SEL 上 34.8% vs LLaMA‑405B 29.0%）。
  - **多跳推理**：性能随跳数增加急剧下降（Figure 3），除 GPT‑5.5 外多数模型损失超 50% 准确率；2‑跳 RAG‑API 问题出现性能回升（可能与 Dashboard 表现相关）。
  - **多跳多源与策略遵循**：GPT‑5.5 平均 26.0%，其他模型 11–18%；策略约束任务中，不可答问题表现极差（Claude‑Opus‑4.7 仅 2.4%，其余 3.7%），表明模型难以识别策略使问题无法回答的情形。
- **错误分析**（Table 4、5）：
  - **SEL vs SLOT 错误模式**：SEL 错误均匀分布于各阶段（工具识别→参数名→参数值），SLOT 在参数值阶段骤降明显。
  - **接地错误分类**：幻觉（unsupported claims）占主导（BI API 82–95%、Dashboard 54–77%），提取失败（解析/截断长响应）在 Dashboard 中更常见（38%）。
  - **跨源实体消歧**（Table 6、7）：多跳多源中实体消歧成功率约 20–33%；RAG 后接 API 的链错误中近 70–75% 归因于答案提取/接地。

## 相关工作脉络
- **可执行基准**：对比 LiveAPIBench（Elder et al., 2026）仅覆盖 2,500 个实时 API，VAKRA 扩展至 8,000+ 静态可执行 API 并增加文档检索；区别于 ToolBench、RestBench 使用外部不稳定 API。
- **多跳推理**：工具调用多跳基准（ToolHop）缺乏跨源组件；多跳 QA 基准（Multihop‑RAG）未结合结构化数据；VAKRA 首次将 API 序列、检索增强与自然语言策略串联于单条轨迹。
- **策略遵循**：τ‑bench 虽评估工具使用策略，但仅限对话域且无跨源 grounding；SOPBench 关注标准操作规程，但未涉及 API‑文档混合场景。
- **评估方法**：多数基准采用最终答案精度或单独工具调用准确率（BFCL）；VAKRA 提出轨迹级重放验证，可区分工具选择、参数填充、信息提取、策略遵守等细分错误。

## 局限性与未来方向
- **数据规模与领域覆盖**：当前 62 个领域主要来自 BIRD‑SQL 公开数据库，可能未充分覆盖垂直企业场景（如金融合规、医疗隐私）；未来可扩展至更多真实行业数据源。
- **生成流水线依赖 LLM**：多跳查询自动合成都依赖 LLM，可能存在隐性 bias 或难以完全消除的答案泄漏；需更 robust 的质量控制机制。
- **评估成本**：完整基准需要运行 4 个 Docker 容器并执行大量工具调用，计算开销较高，限制了大规模模型比较。
- **策略约束表达形式**：当前策略为简单自然语言声明，未探索复杂条件策略（如时间窗口、角色权限）的评估。
- **跨语言支持**：基准目前仅为英文，需国际化才能评估多语言智能体。

## 研究启发与可借鉴点
- **轨迹级重放验证**：对工具调用基准设计极具参考价值——通过重放预测动作并与真实环境交互，既能容忍路径等价性，又能精确到每一步的成功与否，可迁移至其他 agent 评估场景。
- **瀑布式错误筛除分析**：将总错误分解为工具名→参数名→参数值→接地答案四个累积阶段，能清晰揭示不同 API 交互风格下的瓶颈差异，该方法适用于任何工具使用评测。
- **固定智能体骨架隔离变量**：使用统一 ReAct harness 包裹所有模型，确保分数差异反映模型能力而非编排工程，此设计可作为公平 benchmark 的标准实践。
- **跨源可答性过滤**：确保 API 与文档查询互不重叠，避免训练/评估数据污染，这一原则可推广至多模态或多源学习。
- **策略约束的确定性检查**：不仅评估答案正确性，还独立验证工具调用是否符合策略（如禁止使用某数据源），为安全敏感应用提供了评估思路。

## 关键术语表
- **VAKRA**：eValuating API and Knowledge Retrieval Agents 的缩写，本文提出的多跳推理评测基准。
- **Tool‑Use Policy**：用自然语言描述的工具使用约束规则，规定哪些工具或数据源在特定查询下可用或禁用。
- **ReAct Harness**：基于 Reason‑Act‑Observe 范式的智能体执行框架，本文固定使用该骨架以隔离模型推理能力。
- **MCP (Model Context Protocol)**：智能体与工具服务器之间的通信协议，通过 stdio 传递工具定义与调用结果。
- **Slot‑Filling API**：一组通用工具（如过滤、聚合）需要通过填充参数槽位组合完成查询，对应 SLOT 风格。
- **Cross‑Source Grounding**：将非结构化文档中的实体或信息对齐到结构化 API 的参数要求中的过程。
- **Grounded Answer**：最终答案必须完全基于工具响应与检索文档，不允许引入外部知识或幻觉。
- **Trajectory‑Level Verification**：不要求严格匹配工具调用顺序，而是重放整个预测序列并对真实环境执行，比较结果集合是否与 ground truth 一致。

## 可复现要素
- **数据集**：HuggingFace 公开（https://huggingface.co/datasets/ibmresearch/VAKRA），含调优/测试划分、工具描述、知识图谱、文档索引。
- **代码**：GitHub 开源（https://github.com/IBM/VAKRA），提供基准运行器、智能体包装、评估脚本。
- **环境**：单一 Docker 镜像 `benchmark_environ`，通过 `make setup` 一键下载数据、构建镜像、启动容器；嵌入模型已固化，无需运行时网络。
- **关键超参**：
  - ReAct 循环最大迭代次数：由 `recursion_limit` 控制（默认未明确，见 Appendix H.1）
  - 工具短名单 top‑k：可选配置
  - 温度设置：评估 judge 使用 temperature=0
  - 查询超时：`AGENT_TIMEOUT_SECONDS`（具体值见代码）
- **模型**：闭源模型通过官方 API 调用，开源模型通过 vLLM 在 NVIDIA GPUs 上服务（详见 Table 12）。
