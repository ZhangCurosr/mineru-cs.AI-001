# 论文速读：Persistent Recursive Worlds Enable Autonomous Software Evolution

## 一句话总结
论文提出 EvoX Genesis 系统，将软件项目本身作为持久化的递归世界，使有限寿命的 AI 代理能在不同基础模型下接力开发；实验证明该系统可从零构建出完整 C 编译器（120+ 小时、$44 成本），并支持跨模型延续开发以及 MESA 科学代码的 Fortran→Rust 重构，同时保留经过审计的数值行为。

## 研究问题与动机
- **长周期软件开发的连续性困境**：现有 agentic 软件工程系统依赖持久会话、记忆机制、管理器或共享上下文来维持连续性，这些方法本质上是在延长或固化某个智能体的进程，导致“代理生命周期”与“软件开发过程”绑定。
- **核心问题**：当活跃的代理终止时，什么应当持久化？现有工作多通过扩展代理自身的记忆或状态来解决，但未将“项目状态”作为独立的持久实体进行形式化组织。
- **深层动机**：软件任务的周期有限，但软件系统的生命周期长达数月甚至数年，期间需累积接口、测试、架构约束与历史失败经验；长期开发并非更长的单次编码任务，而是需在贡献者（乃至基础模型）更换时保持连贯的持续过程。
- **研究缺口**：缺乏一种将“持续性”显式赋予项目而非代理的组织形式，亦缺乏在大规模真实场景（如从零构建编译器、科学代码重构）中验证该范式的实证证据。

## 核心贡献（创新点）
1. **形式化持久递归世界模型**：提出基于版本–路径（ν, p）的局部软件世界定义，严格区分局部代理行动、递归委托与已接受事件，实现代理生命周期与项目开发历史的解耦。与现有方法相比，本质区别在于将持续性对象从“代理记忆/会话”转移至“项目版本历史”。
2. **EvoX Genesis 系统实现**：实现有限寿命管理器和执行代理在路径作用域上下文中的工作，仅当变更通过验证‑门控被接受后才推进持久项目历史；与 EvoGit 等去中心化版本协作系统相比，区别在于引入了递归委托与父代理验收机制，而非依赖显式消息传递或共享内存。
3. **大规模绿色field形成实证**：从零构建出一个约 25 万行 Rust 实现的 C 编译器（jcc），在 123.4 小时内归档 1,019 个代理事件，仅消耗 $44.38 模型 token 费用，且通过 c‑testsuite、LLVM、Csmith 等全面外部测试；与 FunSearch/AlphaEvolve 等基于评估器搜索程序变体的系统相比，区别在于遵循单一项目的持续历史而非候选程序种群。
4. **跨基础模型延续开发验证**：在同一完成的编译器世界上，分别使用 GLM 5.2 与 DeepSeek V4 Flash 进行延续开发，两者均能继承相同项目约束并产出符合测试要求的演进版本；与多数仅评估单一模型能力的基准相比，区别在于明确验证了“项目为中心”组织对基础模型替换的鲁棒性。
5. **科学软件重构与数值行为保留**：将 MESA 中 13 个模块（共 139,414 行 Fortran）重写为 Rust workspace（89,946 行），在六个数值工作负载上实现 1.55–6.87× 加速，且 EOS lookup 与 Newton solve 保持位精确；与 ERA 等基于明确质量指标搜索科学软件的系统相比，区别在于强调实现变更后仍需保留经审计的数值行为连续性。

## 方法详解
- **局部软件世界**：每个代理被 situated 于 (ν, p)，其中 ν 为已接受的项目版本（含完整历史、约束、验证结果等），p 为仓库相对路径，界定代理的局部责任范围与修改作用域。世界本身不是代理，无私有意图或对话身份。
- **有限寿命代理**：代理 A_i 在 (ν, p) 中接收目标 g_i，生成候选变更 Δ_i = A_i((ν, p), g_i)；代理的私有上下文与 scratch 状态不携带至后续代理，后续工作从已接受版本与路径重新实例化。
- **递归委托**：父代理可在不改变已接受版本 ν 的前提下，将工作委托至子路径 q，即 (ν, p) → (ν, q)；递归仅将工作定位至更具体路径，不立即推进项目历史。
- **验证门控与持久谱系**：只有被父代理接受的变更才构成已接受软件事件 (ν, p) → (ν', p')，推进版本历史；拒绝的变更不改变 ν，但若将失败信息显式存入上下文、测试或谱系记录，则该记录可成为后续已接受版本的一部分。
- **工程实现**：目录作用域节点从版本控制的 CONTEXT.md 记录组装上下文；已接受变更通过 Git commit 与保护性存档引用存储；提议变更隔离于代理专用分支与工作树；调度器状态、BEAM 进程与临时工作树仅提供执行基础设施，不构成项目持久身份。

## 实验与结果
- **Formation（C 编译器从零构建）**
  - 模型：DeepSeek V4 Flash（xhigh reasoning effort，150,000‑token 上下文压缩阈值）
  - 耗时：123.4 小时；归档代理事件：1,019；最大委托深度：5
  - 产出：248,989 行物理代码（750 个文本文件）；模型 token 费用：$44.38
  - 测试覆盖：c‑testsuite 220/220；LLVM 32/36；Csmith 93/93；LZ4、SQLite 通过；Rust workspace 测试 2,904 通过
  - 结论：有限寿命事件可累积为复杂互依系统，无需单一代理跨越全周期。

- **Continuity（跨基础模型延续开发）**
  - 起点：同一由 GLM 5.2 生成的已完成 jcc 仓库（commit 37216cfa254a）
  - GLM 5.2 延续：98 代理，深度 4，通过保留 LLVM 测试集 1,445/1,448
  - DeepSeek V4 Flash 延续：178 代理，深度 8，通过保留 LLVM 测试集 1,820/1,820
  - 结论：相同已接受项目在不同基础模型下均可继续发展，产出不同的代理计数、委托深度与代码变更量，但均继承并遵守已有测试约束。

- **Redevelopment（MESA 模块 Fortran→Rust 重构）**
  - 模型：DeepSeek V4 Flash
  - 耗时：33.22 小时；Spawn 代理：272
  - 产出：89,946 行 Rust 代码（含测试与 benches）；1,052 测试全部通过，18 忽略；模型 token 费用：$10.64
  - 数值验证：六个独立工作负载中，EOS lookup 与 Newton solve 位精确；其余四个相对校验和差异 5.1×10⁻¹⁵–3.1×10⁻⁹
  - 性能：Rust 在所有六个工作负载中位数运行时间均优于 Fortran，加速比 1.55×–6.87×
  - 结论：在实现大幅变更的同时，可保留经审计的数值行为连续性。

- **最强结果与提升**
  - 编译器从零形成：120+ 小时、$44 成本、25 万行代码、完整外部测试通过
  - 科学重构：6 个工作负载全部通过数值验证，中位数加速最高达 6.87×，成本仅 $10.64
  - 跨模型延续：同一编译器在 GLM 5.2 与 DeepSeek V4 Flash 下均保持测试通过率，验证组织形式的模型无关性

## 相关工作脉络
- **SWE‑bench / SWE‑agent / OpenHands**：聚焦 issue‑level 修复或通用平台；Genesis 转向长周期多阶段演化，强调项目状态而非代理记忆作为连续性载体。
- **NL2Repo‑Bench / SWE‑EVO / RoadmapBench**：评估基准延伸至版本升级与序列变更；Genesis 提供实现此类演化的组织框架，并以实证验证大规模形成与重构。
- **EvoGit**：去中心化多代理代码版本重组，无需集中协调；Genesis 引入递归委托与父代理验收，使历史推进受控于验证门控而非自由合并。
- **FunSearch / AlphaEvolve / ERA**：通过评估器搜索程序变体或科学软件；Genesis 跟踪单一项目的持续历史，而非种群搜索树，并强调数值行为保留。
- **Reflection / Memory / Multi‑agent 协调**：通过记忆机制、技能库或角色工作流维持连续性；Genesis 不否认这些机制的价值，但将持续性显式置于项目版本历史。
- **科学软件工程（MESA、FAIR 原则）**：研究代码重现性依赖环境与控制版本；Genesis 的 MESA 重构实验直接回应 AI 辅助变更可能威胁科学软件质量的警告，证明可保留经审计数值行为。

## 局限性与未来方向
- **机制因果性未完全分解**：递归虽在实验中广泛使用（深度 4–8），但未与扁平组织、替代验收机制进行对照消融，无法断言递归为必要因果因素。
- **持久记录必要性未知**：延续实验显示跨模型开发可行，但未隔离出哪些版本历史、上下文文件或谱系记录是必需的。
- **人类干预未完全排除**：实验归档记录目标、工具与控制器限制，但未审计所有人类操作；不能断言零人类参与。
- **评估基准局限**：测试集在不同快照间不一致（如保留 LLVM 测试集随版本变化），跨模型性能比较受限；线计数仅反映仓库规模，未度量复杂度或功能完整性。
- **未来方向**：控制实验固定可执行代码而改变非代码记录、固定项目状态比较持久/有限寿命代理、扁平 vs 层次验收消融、扩展至更多科学领域与更大规模生态重构。

## 研究启发与可借鉴点
- **项目为中心的组织范式**：将持续性置于版本历史而非代理记忆，可迁移至任何需长周期、多贡献者（或换模型）协作的软件开发场景。
- **路径作用域与递归委托解耦**：局部世界 (ν, p) 将责任范围与项目状态分离，便于并行代理分配与增量验证，适合复杂仓库的模块化开发。
- **验证门控与谱系记录结合**：拒绝的变更可将其失败信息显式存入上下文，使后续代理避免重复错误；该方法可集成至现有代码评审流水线。
- **低成本长周期开发实证**：$44 构建完整编译器、$10 完成科学重构，证明 token 效率与长周期可行性，为资源受限的自主开发提供实践参考。
- **数值行为保留作为重构硬约束**：在科学软件迁移中，将已审计数值指标（位精确、相对误差界、加速比）作为验收条件，可确保 AI 重构不损害科学可信度。

## 关键术语表
- **Persistent Recursive World**：以已接受版本与路径为核心的软件开发组织形态，代理有限寿命、项目持续演进。
- **Local Software World w=(ν,p)**：代理所在的工作语境，ν 为已接受项目状态，p 为仓库相对路径，界定代理的责任范围。
- **Finite‑lived Agent**：在单次 episode 内运行、私有状态不跨代传递的代理，仅负责提出局部变更。
- **Recursive Delegation**：父代理将任务委派至子路径 (ν,p)→(ν,q) 而不推进版本，实现工作局部化与深度分解。
- **Accepted Software Event**：通过验证门控的变更 (ν,p)→(ν',p')，是推进持久版本历史的唯一途径。
- **Validation‑gated Acceptance**：父代理基于测试、约束与集成证据决定是否接受、拒绝或要求更多工作的机制。
- **EvoX Genesis**：实现上述理论的系统，采用目录作用域节点、Git commit 与代理专用分支隔离提议变更。
- **MESA（Modules for Experiments in Stellar Astrophysics）**：开源一维恒星演化计算套件，本文作为科学软件重构的典型对象。
