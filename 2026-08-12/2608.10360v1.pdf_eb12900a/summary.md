# 论文速读：MazzikaAI: A knowledge-based performance-to-prompt compiler for real-time Arabic maqam accompaniment with a streaming text-to-music model

## 一句话总结
本论文提出了 **MazzikaAI**，一个基于知识（专家系统）的实时互动伴奏系统。其核心创新是将**自然语言提示作为控制律**，通过确定性编译器将演奏者的实时 MIDI、手势与和声状态编译为连续更新的文本提示，从而驱动一个**无需微调**的流式文本到音乐基础模型（Google Lyria RealTime），实现了对非西方调式音乐（以阿拉伯马卡姆为代表）的微分音伴奏与对话式互动。

## 研究问题与动机
1.  **非西方音乐传统的缺失**：主流生成音乐模型的训练框架以西方十二平均律为基础，阿拉伯马卡姆音乐（以微分音、特性装饰音和模态静置音为特征）在训练数据和控制词表中均严重 Representation 不足。
2.  **实时伴奏的“响应性”鸿沟**：流式文本到音乐模型能增量生成高质量音频，但缺乏细粒度、实时的控制接口。静态提示只能生成通用背景音轨，无法像乐手一样“监听-回应”独奏者。
3.  **控制与音质权衡的困境**：传统的符号/规则系统能提供精细控制但缺乏真实音色；端到端音频生成模型音质高但控制困难，且适应新调式通常需要昂贵的数据收集与微调。
4.  **Prompt Engineering 的范式局限**：现有提示工程多为一次性、离线操作，尚未被发展为驱动实时音频生成系统持续反馈控制律的机制。

## 核心贡献（创新点）
1.  **将提示编译构建为实时控制律**：将交互伴奏形式化为从实时性能状态到自然语言提示的确定性编译过程 $C: (s_t, q_t) \mapsto p_t$，使未微调的流式生成模型成为响应式伴奏者。**与已有工作的本质区别**在于，将 prompt 从一次性查询转变为持续更新的、由确定性规则驱动的“执行器”。
2.  **构建以马卡姆为中心的可检查知识基础**：手工撰写了一个涵盖六核心马卡姆（如 bayati, rast）、特性装饰音、静置音、负向引导（避免西方大调/小调）以及九种西方流派的提示级知识库。**与已有工作的本质区别**在于，用明确、可调试的自然语言规则替代了针对特定调式的模型微调，实现了文化特质的“注入”而非“学习”。
3.  **确定性的网关控制与双引擎架构**：设计了基于性能状态粗粒度特征（和声指纹、短语阶段等）的控制签名 $\sigma$，仅在 musical meaningful 状态变化时触发重提示，并分离旋律引擎与节奏引擎以解决节拍锁定的冲突。**与已有工作的本质区别**在于，在不改变生成模型的前提下，通过外部分层架构和网关逻辑解决了流式模型的稳定性与灵活性矛盾。
4.  **免微调的端到端原型系统与实证评估**：部署了完整的浏览器-后端-云模型原型，并提供了系统延迟分解、网关稳定性测量及对照消融实验（马卡姆接地、仪器抑制、网关开关）。**与已有工作的本质区别**在于，提供了在真实延迟预算内（中位延迟263ms）实现非西方微分音风格互动的完整技术路径与量化证据。

## 方法详解
MazzikaAI 是一个三层系统（浏览器客户端、Python 后端、云端生成模型），通过 WebSocket 连接。

1.  **性能状态估计 ($\Phi$)**：后端维护一个长度为 128 个事件的工作记忆窗口，估算状态 $s_t$。关键特征包括：
    *   **音区/纹理**：平均音高、同时按键数。
    *   **旋律运动**：基于最近 5 个音头的音高差符号（上升/下降/静止）、旋律中心及其方向。
    *   **短语分割**：基于静音间隙（<0.35s 为连奏，>0.4s 为乐句结束，>2.5s 为长停顿）。
    *   **和声推断**：实时和弦识别（模板匹配）与基于 12 小节布鲁斯结构的隐含和弦推断。
    *   **和声指纹**：2秒窗口内音级集合的量化快照（2半音桶），用于稳定重提示网关。

2.  **四态伴奏控制器 ($\pi$)**：根据状态将表演映射为四种行为之一：
    *   **Supporting（支持）**：独奏者演奏时，乐队低密度、低温度地伴奏。
    *   **Responding（回应）**：乐句结束后约 0.3–2.5 秒的“应答窗口”，提示包含独奏者刚演奏的音高序列。
    *   **Sustain（延续）**：单音持续 >2.5 秒时，伴奏保持极简。
    *   **LongIdle（长空闲）**：静音 >5 秒后，乐队主动引领，使用高温度、高密度进行即兴。

3.  **生成参数向量 ($\Theta$)**：每个 $(q_t, s_t)$ 组合映射到一组超参数 $\theta_t = (temperature, top\text{-}k, guidance, density, brightness)$。例如，Supporting 状态使用低 temperature/high guidance 以保持严格跟随；LongIdle 使用高 temperature 以鼓励探索。

4.  **确定性提示编译器 ($C$)**：将 $s_t$ 和 $q_t$ 编译为自然语言字符串 $p_t$。提示结构是有序的子句拼接：
    *   `[乐器约束/静音]` -> 解决 API 无 stem-level 控制的问题，明确指定当前激活乐器并**强烈禁止**非激活乐器发声。
    *   `[特定 header / session stage]`
    *   `[马卡姆行]` -> 核心接地机制，详细描述音阶拼写（如 "E-half-flat"）、特性音级、装饰音、静置音及负向引导（"avoid western major or minor tonality"）。
    *   `[和声上下文 / 回声]` -> 在 Responding 状态下，将 `last_phrase_pitches` 直接嵌入提示，要求模型“回答”或“回声”。
    *   `[角色分配]` -> 根据乐器偏好列表和当前状态，为每个段落分配 supporting/responding/solo_responding 文本描述。
    *   `[音区]` -> `[动态]` -> `[空间子句]`。

5.  **网关控制**：系统在每个 tick 计算粗粒度控制签名 $\sigma$。仅当 $\sigma(s_t, q_t, \theta_t) \neq \sigma(s_{t^-}, q_{t^-}, \theta_{t^-})$ 时才推送新提示。这过滤掉了音符层面的随机波动，只对和声、短语阶段、活跃乐器组等“有意义”的变化进行重提示。

6.  **双引擎流式处理**：
    *   **旋律引擎**：无固定 BPM 锁，根据和声/状态变化重提示。使用 `mute_drums=True`。
    *   **节奏引擎**：BPM 锁定，持续播放 4/4 拍的打击乐床，仅在有风格切换或 BPM 变化时重连。
    *   **客户端音频调度**：使用 Web Audio API，带 -40ms（旋律）/-20ms（节奏）的负重叠进行交叉淡入淡出，并设有“下次启动”游标以处理缓冲和重置。

## 实验与结果
*   **数据集**：系统以阿拉伯马卡姆（特别是 bayati）为核心设计目标。评估主要在一个约 8.5 分钟的**现场现场布鲁斯即兴会话**上进行（作者本人演奏，1516 个 MIDI 事件）。同时使用了 Replay Harness 对同一输入进行**控制消融实验**。
*   **评估基线/消融条件**：
    1.  **马卡姆接地 (A vs B)**：完整接地提示 vs. 替换为等长的通用西方音阶短语。
    2.  **乐器抑制 (A vs C)**：完整提示 vs. 移除开头的乐器约束/静音子句。
    3.  **网关开关 (On/Off/Static)**：网关开启（默认） vs. 网关关闭（每次评估都重提示） vs. 静态（仅编译一次，从不重提示）。
*   **主要结果**：
    *   **延迟**：中位端到端延迟（从按键到可听音频更新）为 **263 ms** (p95: 818 ms, p99: 945 ms)，落在控制器设计的 0.3-2.5 秒应答窗口前端。知识编译层本身耗时 < 0.5 ms。
    *   **网关稳定性**：平均 **179 次重提示/分钟**，在整个 8.5 分钟会话中**零失败**（无队列溢出、无重连、无流中断）。即使网关关闭（202 次重提示/分钟），流依然稳定，表明网关的主要价值是**API 经济**（吸收 43.9% 的评估），而非防止流崩溃。
    *   **马卡姆接地效果 (pYIN 分析)**：使用接地提示时，**22.4%** 的有声音帧偏离 12-TET 半音 >= 35 个音分，远高于消融组的 14.9%。在 bayati 马卡姆的二音级区域，**59.4%** 的接地帧落在四分之一音带（125-175 音分）内，而消融组仅为 24.1%。
    *   **网关消融**：静态提示模式下，触发到音频延迟崩溃至约 **35 秒**，量化了编译器带来的响应性价值。
    *   **专家演奏会话定性反馈**：两位专家乐手认为伴奏在**语义上**是协调的对话，但指出乐队保持了一个**近乎恒定的节拍**，未能随独奏者的呼吸而弹性伸缩（即缺乏节拍级别的对齐）。
    *   **乐器抑制消融**：使用 PANNs 音频标记器审计发现，添加负向抑制子句并**未显著降低**被禁止乐器的检出率，甚至略有增加，表明提示级约束无法替代 API 级的 stem 控制。

## 相关工作脉络
1.  **知识基础音乐系统**（如 CHORAL, EMI）：本文继承了其**可检查的手工规则库**和**确定性推理**的核心思想，但将执行器从符号合成器替换为消费自然语言的预训练流式生成模型，实现了从符号输出到音频输出的跨越。
2.  **交互式即兴系统**（如 Voyager, Continuator, BoB, ReaLJam）：本文同样实现了“监听-解读-回应”的对话周期，但其回应不是通过定制的符号作曲家或强化学习调谐的变压器生成，而是通过编译成文本提示来驱动一个通用的音频基础模型，降低了风格迁移的适配成本。
3.  **文本条件音乐生成模型**（MusicLM, MusicGen）：这些模型提供了强大的生成能力，但控制粒度粗（整体提示）或需要微调以适应新风格。MazzikaAI 在不修改模型权重的情况下，通过外部的确定性编译器获得了细粒度的、实时的控制。
4.  **流式音频模型**（Lyria RealTime, Magenta RealTime）：本文直接建立在 Lyria RealTime 之上，但指出了现有系统仅提供“控制表面”而缺乏“控制策略”的空白。MazzikaAI 填补了这个空白，自动将性能状态编译为持续更新的提示。
5.  **计算马卡姆研究**：过往工作侧重于**分析**（调音、分类），生成工作稀少。本文通过**提示级接地**（明确拼写四分之一音、装饰音、负向引导）而非重新训练，为生成地道的微分音模态音乐提供了一条新路径。

## 局限性与未来方向
1.  **宏观约束控制失效**：提示中的负向抑制（如“此乐器绝对无声”）未能有效阻止模型生成该乐器的声音，表明在缺乏 stem-level API 控制时，纯文本约束存在根本性局限。
2.  **节拍与时间同步缺失**：系统能很好地控制伴奏“弹奏什么”，但无法控制“何时弹奏”。旋律引擎跟随的是语义状态（和声、短语结束），而非独奏者的实际节拍相位，导致 expert 评价为缺乏呼吸感。
3.  **依赖专有托管模型**：系统绑定于 Google Lyria RealTime API，存在网络延迟下限、可用性风险、配额限制以及无法本地化运行的问题。
4.  **知识覆盖范围有限**：和声推断规则主要针对布鲁斯 12 小节结构，未泛化到任意调性；状态估计器假设单人键盘演奏；语音命令仅支持英语。
5.  **缺乏大规模感知评估**：目前仅有两位专家乐手的定性评估和客观音频分析，尚未经过更大规模的用户盲听研究来验证微分音真实性、音乐性等主观质量指标。

**未来方向**：(1) 引入**节拍跟踪与 tempo following**，从音头流中估计独奏者节拍并重新锚定生成引擎；(2) **重新校准网关**，调整和谐波指纹的粒度或增加迟滞，以优化重提示频率与音乐连贯性的平衡；(3) 进行**扩展的受控听觉研究**，验证微分音准确性及音乐满意度；(4) 将编译器**重定向至开源流式模型**以实现设备本地运行。

## 研究启发与可借鉴点
1.  **“提示即控制律”的架构范式**：对于任何具有自然语言输入接口的黑盒生成模型（如图像、视频、代码生成），都可以借鉴此范式——构建一个外部的、确定性的、领域知识驱动的编译器，将实时传感器/用户状态流编译为连续更新的提示，从而实现精确、可解释的闭环控制，而无需访问模型内部。
2.  **免微调的文化/风格注入**：对于小众或非主流的风格（如民族音乐、特定艺术流派），与其收集数据微调大模型，不如将领域专家知识（音阶、规则、禁忌、典型模式）转化为结构化、分层的**提示模板和负向引导语**。这种方法成本低、可审计、可迭代。
3.  **网关控制权衡**：在实时生成系统中，频繁更新提示可能导致不稳定或抖动，而更新太少则缺乏响应性。本文提出的基于**粗粒度性能特征**（而非原始事件）的网关机制是一个有用的设计参考，关键在于找到能区分“有意义变化”与“噪声”的特征抽象层级。
4.  **双通道解耦设计**：将需要不同时钟域的控制任务（如自由节奏的旋律对话 vs. 严格节拍锁定的节奏铺底）分离到**独立的生成实例**中，并通过外部协调器管理其生命周期，可以有效规避单一生成器在混合约束下的内部冲突。
5.  **可复现的评估基准建设**：论文发布的 replay harness 和仪器化日志使得在相同输入下公平比较不同配置或模型变得可行。未来工作可借鉴此方法，建立针对实时互动生成的标准评估协议。

## 关键术语表
*   **Arabic Maqam**：阿拉伯音乐调式体系，以特定的微分音音阶、特征音级、装饰音型（ornaments）和静置音（resting tones）为结构基础，强调即席性和情感表达。
*   **Streaming Text-to-Music Model**：流式文本到音乐模型（如 Lyria RealTime），能够从文本提示中增量生成音频流，允许在生成过程中更新提示。
*   **Knowledge-Based System / Expert System**：基于知识的系统/专家系统，将特定领域的专业知识编码为可检查的规则库，并通过确定性推理从工作记忆中得出结论。
*   **Prompt Compilation**：提示编译，指将非文本的实时状态数据（MIDI事件、估计的和谐等）通过确定的规则转换为自然语言提示字符串的过程。
*   **Maqam Grounding**：马卡姆接地，通过在提示中明确描述马卡姆的音阶拼写（包括四分之一音）、特性音级、装饰音和静置音，并结合负向引导，来将生成模型“锚定”在非西方调式体系中。
*   **Call-and-Response**：呼唤与回应，一种音乐互动模式，指独奏者（呼唤）演奏一段乐句后，伴奏者（回应）以相似或对比的乐句进行答复。
*   **Harmony Fingerprint**：和声指纹，对最近时段内音高集合的粗略量化表示（如2半音桶），用于稳定重提示网关，避免因单个旋律音符而频繁触发。
*   **Gating**：网关，控制系统在何时将新编译的提示发送到生成模型的机制。本文采用基于状态变化感知的网关，以平衡响应性与流稳定性。

## 可复现要素
*   **数据集**：系统针对阿拉伯马卡姆音乐（bayati 等）和布鲁斯等风格设计。论文使用的是作者本人录制的实时演奏会话。
*   **代码**：**已开源**。论文声明源代码已发布，并提供了包含系统源码、主会话仪器日志、replay harness、消融实验每臂日志、分析脚本及生成音频片段的完整复制包（存储于 figshare，DOI: 10.6084/m9.figshare.XXXXXXX）。
*   **权重/模型**：**未开源**。系统驱动的是通过公共 API 访问的托管模型 **Google Lyria RealTime**。
*   **关键超参**：网关评估特征包括 genre, maqam, 状态标志, 和声指纹, 前四个回声音高, 活跃节段集, verse stage, 舍入后的密度/亮度, BPM, 检测/隐含和弦。网关对心跳驱动决策的吸收率为 74.4%，对音符驱动决策的吸收率为 15.1%。重提示速率约 179次/分钟。客户端音频调度使用 -40ms (旋律) / -20ms (节奏) 的负重叠。
